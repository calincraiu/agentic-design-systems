# Agentic Design Systems: course repo (instructor copy)

This is the **instructor's** working copy of a 12-hour Masters module on agentic workflows for computational design. Students are architects, mostly not programmers. You're helping the instructor build and maintain the course.

Students never work in this repo. They get a zip of it (the "course folder"), made by `uv run scripts/package.py`. In that zip, `packaging/student/CLAUDE.md` and `packaging/student/.claude/settings.json` replace this file and the settings. The student versions tell Claude not to edit anything, and deny edits. Students build in **their own, separate folder**, starting empty, and copy in the kits.

## Repo map

| Path | What it is |
|---|---|
| `app/` | The course app (FastAPI). `main.py` serves slides and runs the kit tools; `static/app.js` holds the widgets |
| `slides/<deck>/NN-name.md` | One Markdown file per slide (see "Writing slides" below). `{{COURSE_DIR}}` becomes the folder's full path |
| `slides/figures/*.svg` | Diagrams, drawn as SVG and loaded by `<div data-widget="figure" data-name="...">`. `loop.svg` is generated by `scripts/make_loop.py` (or edit it by hand); `skyline.svg` by `scripts/make_images.py` |
| `slides/*.md` | Reference pages (for example `concepts.md`) |
| `kits/<name>/` | What students copy into their own folder, laid out as a project (`tools/`, `.claude/skills/`, ...). **The only copy of each tool**: the app runs these files directly |
| `.claude/skills/` | Course-folder skills: `setup`, `start`, `course-tutor` |
| `packaging/student/` | Files that replace their repo versions in the student zip |
| `scripts/package.py` | Builds `dist/ads-course.zip` |
| `scripts/make_images.py` | Regenerates `app/static/img/*.png` (the hook's contact sheet) and `slides/figures/skyline.svg` from the real tower tool |
| `instructor/` | Run-sheets and notes (left out of the zip) |
| `tests/` | `uv run pytest` (left out of the zip) |

## Writing slides

A slide is one Markdown file. Line 1 is a comment with its settings, separated by bars:

```
<!-- layout: task | where: code-yours | time: 25 min | pairs -->
```

- `layout`: `title`, `section` (a chapter title before each part of the session: kicker, h1 and a `<p class="lead">`; concept sections add the `parts` figure with `class="map"` as a "you are here" map), `statement`, `stage` (a widget fills the slide), `split`, `diagram` (a figure on a grid) or `task` ("your turn": a numbered list becomes step cards).
- `where`: `chat`, `code-yours`, `code-course` or `app`. It shows as a chip in the title block, so students always know which window and folder to be in.
- Below a line `<!-- notes -->` go **study notes for students**: they read them after class (press `N`, or reading mode), so write to the student ("you"). Use a shape like **The idea.** / **Why it matters.** / **Try it yourself.**, about 100–200 words. **Keep slides to one claim and one visual**, and put the explanation in the notes.
- Cues meant only for the instructor (what to press, what to ask the room, what to watch for) go in the **Slide by slide** table in `instructor/session-1.md`, never in the notes. Students can see the notes.
- Widgets (`add`, `dice`, `llm-vs-tool`, `tower`, `file`, `skill`, `context`, `takeaway`, `gallery`, `contact`, `figure`) are `<div data-widget="...">` tags. `add` takes `data-numbers` and, with `data-poll`, checks the room's answers against the tool. `llm-vs-tool` is the fairness poll and takes `data-options`. `takeaway` takes one kit or several (`data-kit="add,dice"`). `figure` takes `data-name`, `data-start="n"` (parts already showing when the slide opens) and `data-ghost` (show unrevealed parts faintly).
- In a figure, any element with `data-step="n"` appears on the n-th key press. Steps count up from 1 with no gaps (`tests/test_app.py` checks).
- Every slide in `session-1` must declare a layout and a `where`. The tests check that, that every widget's file, kit, figure and image exists, and that no slide names a path on one particular computer (the take-away prompts find the course folder at runtime).

## Rules for the kits

- Each tool must run in an **empty folder** with `uv run tools/...`: a `# /// script` header lists its dependencies, and output goes to the current folder (`runs/`).
- Each kit's `.claude/settings.json` must be **identical**, so copying a second kit is harmless. `tests/test_kits.py` checks this.
- `add.py`, `dice.py`, `tower.py` and `stair_check.py` are meant to be read by students. Keep them short and plain. `drawing.py` and `gallery.py` are plumbing.

## Tools and app

- `uv run course`: start the app (free port from 8765, opens the browser; `--no-browser`).
- `uv run pytest`: tests, including that every slide opens and that the kits work in an empty folder.
- Don't install other packages or tools without asking.

## Writing for students

Plain language, with architectural examples. Define technical terms the first time. When you write or change student-facing material, say in two or three sentences what it does and why.
