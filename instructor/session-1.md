# Session 1: instructor notes

**Aim.** Students can tell the model apart from the app it runs in, and can tell apart an LLM, a tool, an agent, a skill and context, because they have seen each one do something the others can't. By the end, they have **their own folder** with a `CLAUDE.md`, the add and dice kits, a rule they changed in a skill, and a design stance. No Rhino in this session.

**Two folders, said early and often:** the course folder is the tutorial: followed, run and read, never built in. Their own folder is their project, and it is where all authorship happens.

**The slide notes are for students.** Each slide's notes (`N`, and reading mode) explain the slide to a student revising after class. Everything meant only for you (what to press, what to ask the room, what to watch for) is in the **Slide by slide** table below. This folder is left out of the student zip.

## Run-sheet (about 4 h 15)

The slides are `slides/session-1/` in the course app (`uv run course`): 45 slides, including the end card. They alternate between the app (concepts, widgets) and Claude's Chat and Code tabs (polls, demos and student work). The chip at the bottom right of each slide says where the students should be working.

The session is in chapters, and each one opens with a **section slide** (big title, one lead line). Before Groundwork, a short section ("What answered you?") separates the **model** from the **app**: everything later (Chat vs Code, tools, the receipt, the leash, soft and hard rules) leans on that split. Students set up their own folder during Groundwork, so from the agent section on, **everyone does each demo in their own folder**, not just you. Part 1 meets the parts of the system one at a time, in the order the `parts` diagram builds them: **the LLM, the tool, the agent, the skill, context**, and then you. On each Part 1 section slide, the diagram shows the parts so far, with the rest ghosted. Press `→` once to draw the new part, then move on. Each section uses both running examples: adding up (exact) and rolling dice (fair).

Three threads run through the whole session:

- **The wish.** On slide 3 everyone gives Chat the same tower wish. The tower demo (40) and the stance task (41) use it again, and slide 42 compares the two answers. It is the session's before-and-after.
- **Check the receipt.** Say it every time a tool runs: the explanation is text, the command and its output are the record (18, 28, 31, 37). Slide 26 shows why: the app writes the receipt, not the model.
- **The model writes, the app acts.** Slides 6–7 set it up and 26 shows the mechanism. Come back to it at the leash (29), the 7 on a six-sided die (33) and the which-part slide (37).

**Presenting.** `→` reveals the next part of a diagram before moving to the next slide, `←` hides it again. `N` opens the notes, `G` shows all slides, `R` switches to reading mode, `D` toggles dark/light, `F` goes full screen, and `?` (or the **Keys** button at the top right) lists them all. For a bright projector, open the app once with `?theme=light` on the address (for example `http://127.0.0.1:8765/?theme=light`), and it remembers.

**If you're behind:** shorten the change-a-rule task (33) to a demo of one rule change in your folder, and run the which-part slide (37) as a quick call-out. Keep the stance and the same-wish comparison: they are the authorship and the payoff. The AI-family slide (5) can be a one-minute glance, and the command slide (22) can be shown quickly: students meet commands again in every "Behind the scenes".

**Try these in Chat beforehand.** Six asks depend on how Chat behaves on the day: the tower wish (slide 3), the same question with two models (6), the Pritzker-and-date question (17: is web search on?), the long sum and "how did you work that out?" (18), the fairness poll (19) and `1,5 + 2` (21). Each slide still makes its point if Chat behaves "well", and the notes say how. Still, know what you'll get before the room does.

## Your demo folder

Do the demos in **your own folder**, built with the same take-away kits the students use, not in the course repo. Students then see exactly what they'll do. Before class: make an empty folder, write a short `CLAUDE.md`, copy in the `add`, `dice` and `tower` kits, and run `/tower-designer` once with the slide 3 wish so its `runs/` is ready.

For the hook slide, the app's gallery shows the course folder's `runs/`. To show your own prepared runs instead of the contact sheet, swap the `contact` widget for `<div data-widget="gallery"></div>` in `02-hook.md`, then either build a few towers in the explorer beforehand, or copy your demo folder's `runs/` into the course folder's `runs/`.

**The take-away prompts show *your* path when projected.** That's expected: the app finds the course folder on the computer it runs on, so each student's own app shows their own path. Say it out loud on slide 41 (the first prompt students paste): copy it from your own app, not from the screen. Slide 13 uses a zip instead, so nothing there depends on a path.

## What the tower can't measure (seeds for Session 2)

Whatever wish students bring, these come up. Collect them in the crit: they're where Session 2 starts.

- **Terraces and outdoor space:** no metric for them. The perfect Session 2 seed.
- **Views and orientation:** where the top floor faces, what it looks at.
- **Visibility and memorability:** "seen from the river", "a landmark".
- **Cost and structure:** overhangs are measured (`max_cantilever_m`), their cost and risk aren't.
- **Shadow on the park:** the slide 3 wish asks for it, but the shadow metric is all the ground in shadow at one sun angle. The tool doesn't know where the park is. Expect it in the same-wish comparison (42).
- **Daylight and fairness between floors:** shadow is one fixed sun position on the ground only.
- **Shape limits:** taper is linear, so a tower can't "stay thin and flare near the top". Wanting that is a reason to change the *tool*, not the skill.

## Likely problems

- **Students work in the course folder.** In the student copy, Claude is told not to edit there, and edits are denied. If someone is stuck, check which folder their Code tab has open.
- **The take-away prompt doesn't copy the hidden `.claude` folder.** Ask Claude to list `.claude/skills/` afterwards. Fallback: the "download the kit as a zip" link under each prompt.
- **The take-away prompt has the wrong path.** They copied it from the projector. Copy it from the app on their own computer; the prompt also tells Claude to ask if the folder doesn't exist.
- **A new skill doesn't show up.** Start a new session. If it still doesn't, check the folder is directly in `.claude/skills/<name>/` and the file is called `SKILL.md`.
- **Students can't find `.claude/`.** Dot-folders are hidden in Finder and some file windows. Use the app's file pane, or ask Claude to open or copy the file.
- **The course app stops.** Started with `/start`, it lives as long as that Claude session. Run `/start` again, or use the double-click launcher.
- **Synced folders (OneDrive, iCloud).** These usually work, but can be slow or lock files. Prefer a local folder.
- **Permission prompts.** Each kit's `.claude/settings.json` pre-approves `uv run tools/...`. Anything else prompts, and that's worth a sentence: *the agent asks before acting outside its lane*.
- **Two skills with similar descriptions.** Call them explicitly (`/tower-good-neighbour`) rather than relying on the agent to pick one.
- **The gallery doesn't update.** It's rebuilt after each run, but the page needs a refresh.
